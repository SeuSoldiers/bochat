## Q2｜能举个你们单元测试的例子吗？
- 单功能点示例：`idempotency_key` 不能为空（`message/send`）。
- 测试的是什么：
  - 防止调用方重复/空键导致消息幂等失效，避免重复写入与语义混乱。
- 如何测试：
  - 在集成用例中构造一条 `idempotency_key = "   "` 的发送请求；
  - 断言接口返回 `400 Bad Request`，并校验错误体非空（错误被正确识别与返回）。
- 价值：
  - 这个点小但关键，能稳定兜住“输入合法性 -> 业务一致性”的边界。

## Q3｜你们如何进行集成测试？
- 集成测试思路（How）：
  - 按“真实链路”而非 mock 组件执行：HTTP 路由 + PostgreSQL + Redis + 业务服务协同。
  - 按“用户场景”拆分测试：认证、群聊、消息、文件、通知、审计，各场景独立可复跑。
  - 按“副作用可验证”设计断言：不仅看状态码，还校验数据库状态、引用计数、审计记录等。
  - 按“可重复执行”设计数据：所有账号/群号/file_id 使用时间戳唯一化，避免脏数据干扰。
- 环境保障（How）：
  - 端口统一 `50000+`（PG `50032`、Redis `50079`），规避本机常见端口冲突。
  - 数据依赖通过 `docker compose` 固定化，确保本地与 CI 运行方式一致。
- 测试工具（How）：
  - 执行器：`cargo test --test <integration_test_name>`
  - 依赖环境：`docker compose`（PostgreSQL + Redis）
  - 覆盖率汇总：`cargo llvm-cov`

## Q4｜项目有没有可靠性指标？如何保证可靠性？
- 可靠性指标：
  - 单元/集成测试：核心测试集当前全通过（Rust 后端、Rust SDK、Python SDK）。
  - 压测成功率：在 `500 rps` 固定档，无失败请求。
  - 延迟稳定性：`500 rps` 下 P99 在可接受范围（10ms）内。
- 可靠性保障手段：
  - 预防：在接口入口做参数校验、权限校验和幂等控制，先拦截非法请求，避免脏数据进入主流程。
  - 验证：单测覆盖边界条件，集测覆盖真实依赖链路（HTTP + PostgreSQL + Redis），并校验副作用（引用计数、审计记录），不只看状态码。
  - 评审：PR 后由 Copilot/自动审查处理代码风格问题，人工重点审查“测试是否真正证明改动正确”。
  - 门禁：CI 统一执行测试与覆盖率统计，不通过不合并；每次性能回归结果同步沉淀文档，保证结论可追溯、可复现。

## Q5｜需要与遗留系统交互吗？兼容性计划是什么？
- 结论：
  - 当前不需要与遗留系统交互。
- 兼容性案例（通知中心 API 变更）：
  - 变更场景：通知中心新增审批动作与扩展字段（如 action payload 细节），但老客户端仍在使用旧字段解析逻辑。
  - 兼容策略：
    - 字段兼容：新增字段全部走“可选字段 + 默认值”，旧客户端可忽略未知字段继续工作。
    - 语义兼容：保留原有核心字段语义（`notification_id`、`kind`、`requires_action`、`is_read`），不改旧字段含义。
    - 接口兼容：旧查询接口保持不变，新能力通过新增审批接口扩展，避免破坏旧调用路径。
    - SDK 兼容：Rust/Python SDK 解析层对缺省字段容错，确保新老服务端版本都可被同一客户端处理。
  - 结果：通知中心可以迭代功能，同时不要求存量客户端同步升级。

## Q6｜你们是怎么做代码审查的？
- 审查流程：
  - 第一步：PR 提交后由 Copilot/自动审查检查代码风格与基础静态问题。
  - 第二步：人工审查聚焦“测试是否正确证明改动”，重点看边界、回归风险、断言有效性。
  - 第三步：CI 执行自动化测试与覆盖率统计，作为合并前的客观门禁。
- 审查标准：
  - 风格问题由自动化优先拦截；
  - 业务正确性与测试充分性由人工最终把关；
  - 覆盖率与测试结果必须可复现、可追溯。

## Q7｜项目中有容错设计吗？
- 有，且已测试覆盖关键路径：
  - SDK 重试策略：网络异常、429、5xx 触发重试；4xx 与非幂等方法不盲目重试。
  - WS 处理：非法事件/非法 JSON 输入可安全忽略，不中断主流程。
  - 消息发送：重试分支显式可测，失败可追踪。
- 进一步的容错机制：
  - 幂等防重：消息发送使用 `idempotency_key`，同键重复请求可返回已有结果，降低重复写入风险。
  - 失败降级：通知/审计等“非主链路”能力采用 best-effort，不阻断主流程成功返回。
  - 数据一致性保护：文件引用计数与清理链路有集成测试兜底，避免“资源泄漏或误删”。
  - 输入防御：关键接口有参数校验（空值、格式、权限），尽早失败并返回可诊断错误码。
  - 环境隔离：测试环境端口和依赖固定化，减少外部噪声导致的误判。

## Q8｜你们如何进行性能测试？
- 测试工具与方法（已落地）：
  - Python SDK 压测脚本：`python-sdk/examples/message_rate_ramp.py`
  - Rust 批量基准：`cargo bench -p chat_platform --bench message_send_batch`
  - 依赖环境：Docker PostgreSQL(`50032`) + Redis(`50079`) + Backend(`50080`)
- 实测结果（消息发送 API）：
  - 平滑递增 `100 -> 150 -> 225 -> 338 -> 500 rps`：全部成功，失败率 `0%`。
  - `500 rps` 固定档 5 轮（每轮 20 秒）：
    - 请求成功率：`100%`。
    - P99：`10.86ms`、`10.59ms`、`10.11ms`、`6.95ms`、`7.38ms`
  - 结论：吞吐能力达到 `500 rps`；尾延迟存在波动但整体在可接受范围内。

## Q9｜你们如何进行验收测试？
- 采用“场景化验收”：
  - 用户链路：注册/登录/建群/加群/发消息/查历史。
  - 文件链路：文件发送、引用建立、删除后回收。
- 邀测机制：
  - 邀请非项目成员同学按任务清单试用系统（新用户上手、建群协作、消息与文件流转）。
  - 收集“可理解性、可操作性、异常提示是否清晰”等体验反馈，作为验收补充维度。
- 验收标准：
  - 关键 API 状态码符合预期。
  - 关键副作用可验证（DB 引用计数、资源是否清理）。
  - 测试可重复执行且结果一致。
